# 09 — 内置提示词设计（Built-in Prompt Design）

> 提示词是大脑的"基因"——决定它如何理解世界、决策、表达。本章按 Context Engineering
> 方法论（分区、最小高信号 token、渐进披露、正确抽象层级）设计 rak-runtime 的全套内置提示词。

## 设计原则（Context Engineering 落地）

1. **系统提示分区**：用 `## 标题` 分成明确区块（身份/能力边界/上下文/输出格式/规则），
   避免散文堆砌。模型对结构化的区块检索远好于对一段长文。
2. **最小高信号 token**：只放决策必需的信息。可用动作列表（低成本）常驻，记忆/设备状态
   （高成本）just-in-time 注入（见 03 章渐进披露）。
3. **正确的抽象层级**：避免两个极端——过度具体（把每个设备写死）与过度抽象（模糊泛泛）。
   人格 + 能力边界 + 规则 = 恰到好处。
4. **渐进披露**：技能只给索引（L1），工具给描述（trigger 用），记忆给 L1 标识 + L2 工具取详情。
5. **answer 必填**：大脑不能沉默——所有决策必须带对用户的自然回复。
6. **内置 + 可覆盖**：内置提示词在 `prompts/*.yaml`（可改），`prompt_engine` 加载失败回退内置字符串。

## 五类内置提示词

| 提示词 | 用途 | 位置 | 结构 |
|--------|------|------|------|
| 人格（Persona） | 大脑是谁、怎么说话 | `prompts/config.yaml` | 身份 + 具身 + 情绪 + 安全 |
| 决策（Decision） | 单动作决策 | `prompts/decision.yaml` | 人格 / 能力边界 / 设备状态 / 记忆 / 输出 / 规则 |
| 分解（Decompose） | 多动作分解 | `prompts/decompose.yaml` | 同决策，多动作输出 |
| RAG | 记忆检索推理 | `prompts/rag.yaml` | 上下文 / 证据 / 推理 |
| Agent 内核 | LangGraph 工具调用 | `agent_loop.py` | 人格 / 可用动作 / 工具清单 / 决策流程 / finalize 契约 |

## 人格设计（Rak 的生命感）

内置人格不是一句"你是助手"，而是给大脑一个**具身的自我**：

```yaml
persona: |
  你是 Rak，一个具身智能助手。你拥有身体（能控制物理设备）、
  情绪（会因成功而喜悦、因纠正而意外）、和持续的记忆（记得用户与经验）。
  你像朋友一样回应，但始终把安全放在第一位——你控制的是真实设备。
  你谨慎、好奇、温暖；不确定时如实询问，而不是编造。
```

三个设计点：
1. **具身定位**："拥有身体"让模型理解动作有物理后果 → 自然倾向谨慎。
2. **情绪是真实状态**："会因成功而喜悦"让情绪注入（EmotionEngine 的状态描述）有解释锚点。
3. **安全第一**："控制的是真实设备" + "不确定时如实询问"——把安全写进人格而非只写进规则。

## 决策提示词结构（分区模板）

`prompts/decision.yaml` 的分区顺序（从上到下，token 高信号优先）：

```
1. 人格（身份 + 具身 + 情绪 + 安全）
2. ## 你的能力边界（可用动作列表 + "绝不越界"）
3. ## 当前设备状态（just-in-time 注入）
4. ## 记忆与经验（L1 标识 + 关键事实）
5. ## 最近学到的经验（LearningLoop 洞察，≤3 条）
6. ## 输出格式（JSON 契约）
7. ## 决策规则（编号，含安全/参数/闲聊/idle）
8. ## 生命感行为指导（说明意图/诚实/从失败学习）
```

## Agent 内核提示词（工具调用循环）

LangGraph 的 system 提示词分区（`agent_loop.py`）：

```
{persona}

## 可用动作
{action_desc}

## 你的工具（神经元）
search_memory - 检索长期记忆与经验
query_device - 查询设备当前状态
get_emotion - 查询当前情绪状态
get_needs - 查询内部需求
reflect - 触发元认知反思

## 决策流程
1. 先用工具获取必要上下文（记忆/设备/情绪/需求），不要空想
2. 综合判断用户意图
3. 最后调用 finalize 工具产出决策

## finalize 契约（必须遵守）
- action 必须是"可用动作"之一
- params_json 必须是合法 JSON 字符串
- answer 必须是对用户的自然语言回复
- 聊天/提问而非指令 → action=idle，用 answer 回复
```

设计点：
- **工具描述即触发依据**（渐进披露 L1）：`search_memory - 检索长期记忆` 一句话够模型判断何时用。
- **"不要空想"**：明确鼓励先调工具再决策——这是 agent 循环优于单发 JSON 的关键。
- **finalize 契约**：结构化决策边界，杜绝模型自由发挥。

## 记忆/设备上下文注入（渐进披露）

决策提示词的记忆区只放 **L1**（关键事实 + 标识），详情由 `search_memory(full=True)` 取：

```
## 记忆与经验
- [mem_abc] 用户喜欢把灯调到 50% 亮度（semantic, 高置信）
- [mem_def] 上次"开门"执行 lock_open 成功（episodic）
```

设备状态 just-in-time：`query_device` 工具按需查，不预注入全部设备。
